## 一、范围与目标

按冻结基线实现"单机、前后端分离"的物业管理系统：

1. 后端：本地自承载 HTTP API（OWIN，127.0.0.1:5210），承载全部业务逻辑与数据（SQLite + Dapper）；
2. 前端：WPF 桌面客户端（.NET Framework 4.8 + HandyControl），只做界面、交互与本地打印，不直接访问数据库；
3. 覆盖七大子系统 + 公共支撑，60 个用例、60 张库表、36 个原型页面全部落地；
4. 目标环境：Win7 SP1 / Win10 / Win11 单机，安装包一次装好（客户端 + 后端服务 + 运行时）。

## 二、开发顺序决策（核心结论）

**决策 DZ-2（2026-08-28 项目负责人确认）：骨架先行 → 契约定稿 → 前端/后端实施顺序由项目负责人自由选定。**

| 编号 | 决策点 | 结论 |
|---|---|---|
| DZ-2 | 实施顺序 | M0 搭建中性项目骨架（不依赖也不强制先后顺序）→ M1 契约定稿 → 前端/后端任选其一先开工 |
| DZ-2-1 | 契约前提 | 无论先做哪端，M1 契约须在深入开发前定稿——前后端唯一耦合点是 API 契约 |
| DZ-2-2 | 切片约束 | 不搞"全部后端做完再做前端"，按业务切片纵向推进（每片 = 后端 + 前端 + 验收） |
| DZ-3 | 数据目录 | 统一放 `%ProgramData%\PropertyManagement\`（SQLite 库、日志、备份、导出），避免 Program Files 写入权限问题；影响 Server 路径设计与 Installer 脚本 |
| DZ-4 | 验收策略 | **不使用虚拟机兜底**；验收在项目负责人 Win10 真机完成（全新安装 + 核心流程）；Win7/11 兼容性由开发期红线约束保障，后续由负责人自行抽测 |

理由：

1. 骨架（解决方案、依赖锁定、分层约定、OWIN/WPF 运行骨架、API 客户端基类）为中性工程，与先后顺序无关；
2. 契约不定就开工，两边按各自理解实现，联调必然对不上——这是唯一必须前置的约束；
3. 后端先做可直接用 HTTP 工具自测业务规则；前端先做可按契约 mock、联调前替换，两种顺序都成立；
4. 优先级不变：**财务核心（M4）优先于其他业务子系统**，与原型评审点"收款/账单/欠费"一致；全局框架（M3）先行打通端到端。

## 三、工程结构（初始化目标）

```
PropertyManagement.sln
├─ PropertyManagement.Contract        # 前后端共享契约（DTO、枚举、常量），无外部业务依赖
├─ PropertyManagement.Server          # 本地后端服务（自承载 HTTP API）
│  ├─ Api/                            # 控制器 / 路由（/api/v1）、鉴权中间件
│  ├─ Services/                       # 用例编排服务、事务边界
│  ├─ Domain/                         # 实体与业务规则（BR）
│  └─ Infrastructure/                 # Dapper、SQLite、文件、备份、日志
├─ PropertyManagement.Client          # WPF 前端
│  ├─ Views/                          # 页面与控件（对应 PG-XXX）
│  ├─ ViewModels/                     # MVVM（对应 DM-03）
│  ├─ Services/                       # API 客户端封装
│  └─ Assets/                         # 主题、图标、样式（HandyControl）
└─ Installer/                         # Inno Setup 安装脚本
```

## 七、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 依赖包与 .NET Framework 4.8/Win7 不兼容 | 高 | M0 锁定精确版本；新包只选 net45/net46/netstandard2.0 兼容资产（开发期红线）；发布前负责人 Win10 真机抽测 |
| System.Data.SQLite 原生库位数不匹配 | 高 | 明确 x86/x64 目标平台策略；安装包内置两版原生库或统一位数 |
| 单机双进程联调问题（端口冲突/服务未启动） | 中 | M3 实现启动检查与自拉起；端口可配置（默认 5210） |
| 收据/报表样式与原型偏差 | 中 | M4 内提前验证打印与导出，以原型为基准评审 |
| 纸质台账手动补录工作量大 | 中 | Excel 导入（M5）先行；提供模板与错误清单降低补录成本 |
| 基线变更/需求蔓延 | 中 | 严格走 CHG 变更控制；契约变更必须先评审 |
| 数据文件写入权限（数据目录） | 中 | 数据目录统一 `%ProgramData%\PropertyManagement\`（DZ-3）；安装包预建目录并设置权限 |

## 八、版本与变更控制

1. 本计划 v0.1 为待评审稿，评审通过后升 v1.0 作为开发执行基准；
2. 开发启动后按里程碑拆分子任务列表（如 M1-任务列表.md），逐项勾选状态；
3. 需求/契约/界面变更一律走模型基线变更控制（CHG-xxx），不得绕过；
4. 代码提交遵循"小步提交、可编译可运行"原则，每个切片完成即达可演示状态。
